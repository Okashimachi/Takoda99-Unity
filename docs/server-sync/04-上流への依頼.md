## REQ-01

**宛先**: Takoda99-Proto（issue または PR）
**優先度**: 高 — **これが直るまで表示名機能を実装できない**

### 題目

`MatchmakingJoin.DisplayName` が Go 正典にのみ存在し、C# ミラーに反映されていない

### 本文

`MatchmakingJoin` の `displayName` が **Go 正典にはあるが、C# ミラーに存在しません。**

| 言語 | v0.3.0 時点 |
|---|---|
| Go（正典）`proto/messages.go` | `DisplayName string \`json:"displayName,omitempty"\`` ✅ |
| C# `csharp/Takoda99.Proto/Messages.cs` | `public sealed class MatchmakingJoin { }` ❌ |

コミット `d567a98`（2026-08-04「feat: MatchmakingJoin に DisplayName フィールドを追加」）が **Go のみを変更**し、後続の `55bbe0a`（v0.3.0）でも拾われなかったためと見られます。

**実害**：サーバーは `displayName` を読む実装になっている（`cmd/server/main.go` の `awaitJoinName`）ため、C# の型どおりに `{}` を送ると**全プレイヤーの表示名が空になり、フォールバック名が割り当たります**。サーバー側の結合仕様書 §2.1 も「盤面に名前が出ない不具合の大半はこれ」と記載しています。

### お願いしたいこと

**C# ミラーに `displayName` を追加し、Go 正典と揃えてください。** `omitempty` に対応する形（`JsonIgnoreCondition.WhenWritingNull` または既定値省略）が Go と整合すると思われます。

> **TS ミラーについては、こちらからは依頼しません。** takoda99-unity が使うのは C# のみのため、必要かどうかの判断は Proto 側にお任せします。

**takoda99-unity 側では `pureC#/vendor/Takoda99.Proto/` のミラーを編集しません**（契約の変更は Proto 側で人間承認、という原則のため）。修正版が出たらタグを切っていただければ、こちらで差し替えます。

### 補足

この依頼とは別に、`MatchmakingJoin` の `displayName` を**使う側**の仕様は [Unity/docs/.sdd/matchmaking/](../../Unity/docs/.sdd/matchmaking/README.md) に用意済みです。ミラーが直り次第、実装に着手できます。

## REQ-02

**宛先**: Takoda99-Server（サーバー担当）
**優先度**: 高 — **我慢ゲージは主要UIであり、現状では Late 以降に表示が破綻する**

### 題目

`Patience.LateMul` と `Patience.AlertMs` を `GameParametersPublicSubset` へ公開してほしい

### 本文

#### 1. `Patience.LateMul`（必須）

`internal/game/session.go` の `stepPatience` を読みました。

```go
effectiveDt := dtMs
if s.phase == proto.PhaseLate && s.params.Patience.LateMul > 0 {
    effectiveDt = int(float64(dtMs) / s.params.Patience.LateMul)
}
...
c.patienceLeftMs -= effectiveDt
```

Late フェーズでは我慢ゲージが `1 / LateMul` 倍速（既定 0.6 → 約1.67倍速）で減り、**これは行列内の全客に、来店済みの客も含めて即座に適用される**と理解しました。`patienceMaxMs` は書き換わらず、減る速度だけが変わります。

**我慢ゲージはクライアント側で計測する方針で確定しています**（残量の同期メッセージは要求しません）。一方クライアントに届くのは `patienceMaxMs` と `patienceStartedAtServerMs` の2つだけなので、**線形にカウントダウンすると Late 突入以降ズレ続けます**。1.67倍のズレはゲージ上で明確に見えてしまいます。

クライアントは `PhaseChange` で Late 突入を知っているため、**`LateMul` の値さえ配っていただければ自力で正しく計算できます。** 毎tickの同期は不要で、`MatchStart.params` に1つ入れていただくだけで済みます。

> `patienceMaxMs` を短縮後の値で送り直す方式でも解決しますが、来店済みの客に対する再送が必要になるため、**倍率を1つ公開していただく方が簡単だと考えています。**

#### 2. `Patience.AlertMs`（できれば）

`internal/game/params.go` に `AlertMs`（既定 2000ms）の定義がありますが、**サーバー実装では参照されていない**ようでした（定義と既定値のみ）。実質クライアント向けの表示閾値だと理解しています。

離脱間近の警告表示に使いたいので、あわせて公開いただけると、運営UIでの調整にクライアント側も追従できます。**優先度は `LateMul` より低い**です（届かなくてもクライアント固定値で代替でき、ズレても実害が小さいため）。

### お願いしたいこと

`GameParametersPublicSubset` に以下の追加をご検討ください（Proto 側の型変更が必要になります）。

| フィールド | 型 | 用途 |
|---|---|---|
| `patienceLateMul` | `float64` | Late 以降の我慢ゲージ減少速度の補正 |
| `patienceAlertMs` | `int` | 離脱間近の警告表示の閾値（優先度低） |

### 補足：確認できたこと

「評価の高い店ほど我慢ゲージが速く減るのではないか」という仮説を持っていましたが、**`stepPatience` は評価を一切参照していない**ことを確認しました。評価が上がると**客の分配が増えて行列が伸び、同時に減る客が増える**（＝忙しくなる）という形で難度が上がる設計だと理解しています。速度が変わるのは Late フェーズのみ、という認識で合っていますでしょうか。

**この認識で問題なければ、必要なのは `LateMul` の公開だけです。**

## REQ-03

**宛先**: Takoda99-Server（サーバー担当）／必要なら Takoda99-Proto
**優先度**: 中 — **マッチング画面の参加者一覧が実装できない。人数・締切の表示は現契約で足りる**

### 題目

マッチング中に、参加者の**一覧**（識別子）と**表示名**を配れないか

### 本文

マッチング画面に「**自分を含む参加者の一覧を並べ、自分だけ強調表示する**」UIを用意しました（縦9×横11＝99枠）。ところが現契約では、マッチング中に届く S2C が `MatchmakingStatus` だけで、中身が人数と締切に限られるため、**一覧を描くための情報がありません。**

```csharp
public sealed class MatchmakingStatus
{
    public int  WaitingCount { get; set; }   // ✅ 人数は分かる
    public int  MinPlayers   { get; set; }   // ✅
    public int? CountdownMs  { get; set; }   // ✅ 締切も分かる
    // ❌ 参加者の識別子・表示名は無い
    // ❌ 自分がどれかを示す値も無い
}
```

表示名が届くのは `MatchStart.stores` / `StoreListUpdate.stores`、自分の識別子が届くのは `MatchStart.selfStoreId` で、**いずれも試合開始後**です。

| 欲しい情報 | マッチング中 | 試合開始後 |
|---|---|---|
| 待機人数・締切 | ✅ | — |
| 参加者の一覧・表示名 | ❌ | ✅ `MatchStart.stores` |
| 自分がどれか | ❌ | ✅ `MatchStart.selfStoreId` |

### お願いしたいこと

**マッチング中に参加者の一覧（識別子＋表示名）と、自分を特定する手段を配れないでしょうか。**

ただし、**素朴に `MatchmakingStatus` へ `participants[]` を足す案は帯域面で問題があると理解しています。** 結合仕様書（`docs/client-integration.md` §3.1）と `internal/matchmaking/matchmaking.go` から、join ごとの全員配信を避けて1秒ティッカーに集約している意図（99人同時参加で O(N²)≒4,900通のバーストを避ける）を読み取っています。99人×最大24文字の名前を毎秒フルスナップで配ると、その対策と衝突します。

そのため**具体的な配り方はサーバー側にお任せします。** 考えられる案を挙げますが、どれかを推しているわけではありません。

1. **差分配信** — 参加/離脱した分だけを配る（`participantJoined` / `participantLeft`）
2. **確定時に1回だけ** — カウントダウン開始時など、メンバーが固まった時点で1回フルスナップを配る
3. **ポーリング用の C2S** — クライアントが必要なときだけ一覧を要求する
4. **配らない** — 一覧はマッチング中に見せない仕様とする（この場合はクライアント側のUIを変更します）

**4.（配らない）も十分あり得る回答だと考えています。** その場合はUI側を人数と締切だけの表示に作り替えますので、遠慮なくお知らせください。

### 補足

- 人数（`waitingCount`）と締切（`countdownMs`）だけは現契約で足りており、**マッチング画面の残りの部分は実装済み**です
- クライアント側で名前を生成・補完して埋めることはしません（`StoreSummary.displayName` はサーバーが必ず値を配る、という [SV-11](./01-プロトコル契約の差分.md#sv-11) の取り決めに従います）。空欄で99枠だけ描くことも、実データと乖離するため行いません
- 表示名そのものについては [REQ-01](#req-01)（C# ミラーの追従漏れ）が先に解決している必要があります

## REQ-04

**宛先**: Takoda99-Server（サーバー担当）／必要なら Takoda99-Proto
**優先度**: 中 — **マッチング画面〜試合開始の体験を左右する。現契約でも試合は成立するが、遷移直後がいきなり本番になる**

### 題目

マッチング完了から試合開始までのシーケンスに、**3秒の人数確定待機**と**5秒の開始前カウントダウン**を入れたい

### 本文

#### 目的

現在の契約では、マッチングのカウントダウンが 0 になるとサーバーが `MatchStart` を配り、そのまま試合が始まると理解しています。この形だと**試合画面へ切り替わった瞬間が勝負の開始**になり、画面遷移直後の一瞬でユーザーが状況を把握できないまま押し込まれます。

ここに間を2つ入れて、**「よーいどん」で始まる形**にしたいと考えています。ユーザー側の負荷を下げることが目的です。

#### 希望するシーケンス

```
[マッチング画面]
  1. 参加者が minPlayers に到達
        ↓
  2. マッチングカウントダウン開始（現行の countdownMs）
        ↓
     ┌── 時間切れ ─────────────┐   ┌── 99人到達（時間前）──┐
     │ Bot で 99 人へ補完       │   │ Bot 補完なし          │
     └──────────┬─────────────┘   └──────────┬───────────┘
                └──────────┬─────────────────┘
                           ↓
  3. 3秒待機（この間に Bot 込み 99 人の参加者情報をクライアントへ配信）
        ↓
[試合画面へ遷移]
        ↓
  4. 5秒カウントダウン（サーバーがイベントで配信）
        ↓
  5. 0 になったタイミングで試合開始
```

| # | フェーズ | 長さ | 内容 |
|---|---|---|---|
| 3 | 人数確定待機 | **3秒** | Bot を含む 99 人ぶんの参加者情報を配る。クライアントは 99 枠を埋めて見せる |
| 4 | 開始前カウントダウン | **5秒** | 試合画面に入ってから開始まで。**サーバーがイベントを発行する** |

#### 分岐（Bot 補完の有無）

| ケース | Bot 補完 | 3秒待機 | 5秒カウントダウン |
|---|---|---|---|
| カウントダウンが 0 になった（実プレイヤー < 99） | あり（`99 − 実プレイヤー数` 体） | **あり** | あり |
| 制限時間前に実プレイヤーが 99 人に到達 | なし | **あり** | あり |

**実プレイヤーが 99 人揃った場合は、残りのカウントダウンを待たずに即座にフェーズ3へ進めてください。** その場合も Bot は入りませんが、**3秒待機と5秒カウントダウンは同じように行ってください**（体験を統一したいため）。

### お願いしたいこと

#### 1. Bot を含む 99 人の参加者情報を、試合画面へ遷移する前に配ってほしい

`MatchmakingStatus.participants` は「Bot を含まない・定員補完は試合開始時」という前提だと理解しています（[Proto v0.3.0 のコメント](https://github.com/Okashimachi/Takoda99-Proto)）。フェーズ3では **Bot 込みの確定した 99 人**を配っていただきたいです。

配り方は既存の型を活かす形でも、専用メッセージでも構いません。**判断はサーバー側にお任せします。**

- 案A: `MatchmakingStatus` の最終配信で Bot を含む 99 人を入れる（Bot 判別フラグが要る）
- 案B: 専用の S2C（例 `MatchRosterFixed`）を1回だけ配る
- 案C: `MatchStart` を先に配り、クライアント側で 3 秒間マッチング画面に留まる

> **Bot と実プレイヤーを区別できる値**（`isBot` 相当）があると、クライアントの表示を分けられます。区別を出さない方針であれば、その旨をお知らせください。表示上は同じ扱いにします。

#### 2. 開始前カウントダウン（5秒）と試合開始を、**サーバーのイベント**として発行してほしい

**ここが本依頼の中心です。** カウントダウンをクライアントのローカルタイマー任せにすると、端末ごとに開始タイミングがズレて不公平になります。**残り秒数の配信と、0 になった瞬間の試合開始を、サーバー権威で発行してください。**

| 欲しいイベント | 内容 | タイミング |
|---|---|---|
| 開始前カウントダウン | 残り時間（5秒 → 0） | 試合画面遷移後 |
| 試合開始 | 入力受付・スコア計上の開始 | カウントが 0 になった瞬間 |

既存の `MatchStart` を「試合画面へ入る合図」とし、別途「試合開始」を配る形でも、`MatchStart` に開始予定時刻（サーバー時刻）を持たせる形でも構いません。**後者であれば新規メッセージなしで済むため、そちらのほうが実装が軽いようでしたらそれで問題ありません。**

### クライアント側で行うこと（依頼不要）

- **開始前カウントダウンの5秒間、お題を表示しない制御**は**クライアント側で実装します。** サーバー側の対応は不要です。
- 99 枠の描画・カウントダウンUIの表示・演出もクライアント側です。

### 確認したいこと

1. 現在、マッチングカウントダウンが 0 になってから `MatchStart` が配られるまでに、意図した待ち時間はありますか（実質0という理解で合っていますか）
2. 実プレイヤーが 99 人に到達した場合、現行実装ではカウントダウンを待たずに締め切られますか
3. 3秒 / 5秒という数値は、サーバー側の都合で調整可能でしょうか（クライアントは配られた値に追従します。固定値を埋め込むつもりはありません）
4. 開始前カウントダウン中に切断した参加者は、どう扱われますか（Bot に差し替わる／欠員のまま進む 等）

### 補足

- 参加者一覧そのものについては [REQ-03](#req-03) で別途お願いしています。本依頼はその**配信タイミング**の話です。
- 3秒 / 5秒はクライアント側の希望値です。**サーバーが配る値を正とし、クライアントでは固定値を持ちません。**
