# 02 パラメータと閾値

表示に必要だが `GameParametersPublicSubset` から取得できない値、およびクライアント側で固定値にしてよいかの判断が必要な項目。ステータスの意味は [README §2](./README.md#2-ステータスの表記と運用)。

## 前提：公開パラメータの現状（Proto v0.3.0）

Proto の `GameParametersPublicSubset` は**5項目**。

```csharp
public sealed class GameParametersPublicSubset
{
    public int InitialLife { get; set; }
    public int MaxStores { get; set; }
    public double StormThresholdPct { get; set; }       // v0.3.0 追加：淘汰圏の帯
    public int FinalStageAliveThreshold { get; set; }   // v0.3.0 追加：終盤演出へ切り替える生存店数
    public int FinalRushAliveThreshold { get; set; }    // v0.3.0 追加：最終盤演出へ切り替える生存店数
}
```

> **v0.3.0 で `matchTimeLimitMs` が削除された（破壊的変更）。** 試合の終了条件が「生存店 = 1」のみになり、制限時間という概念が無くなったため（[SV-07](./01-プロトコル契約の差分.md#sv-07)）。

用語集12章の通り、`GameParameters` のフルスキーマはサーバー内部にあり、リモートコンフィグで実行時に変更され得る。**サーバー側でパラメータを調整しても、上記5項目以外はクライアントの表示に反映されない。**

## SV-20

**状態**: 🟡 確認待ち（`stormThresholdPct` は公開済み。**`Patience.LateMul`**・ムード・離脱アラートが未回答）
**題目**: 表示用閾値を公開パラメータに含めるか、クライアント固定値にするか

### v0.3.0 で解決した部分

**最優先だった `stormThresholdPct` が `GameParametersPublicSubset` に追加された。** 「評価3段階の赤帯を淘汰の閾値と揃えたい」という要求（下記「決めたいこと」2）は満たされ、サーバー調整に追従できるようになった。

あわせて `finalStageAliveThreshold` / `finalRushAliveThreshold` も公開され、終盤・最終盤の演出切り替えをクライアント固定値ではなくサーバー配信値で行えるようになった。

さらに [`ForcedEliminationWarning.selfAtRisk`](./01-プロトコル契約の差分.md#sv-05) により、**自店が淘汰圏内かの判定はサーバーが直接配信する**。したがって `stormThresholdPct` の用途は「順位バーに帯を描く」表示のみで、**危険判定に使ってはいけない**（判定はサーバー権威）。

### ★ `Patience.LateMul` の移管（2026-08-06 / [D-11](./03-決定ログ.md#d-11--我慢ゲージはクライアント側で計測する)）

**[SV-03](./01-プロトコル契約の差分.md#sv-03) から移管。本項目で最も実害の大きい未公開パラメータ。**

我慢ゲージは**クライアント側で計測する**方式に確定したが、Late フェーズではサーバー側の減少速度が `1 / LateMul` 倍（既定 0.6 → 約1.67倍速）になる。クライアントは `PhaseChange` で Late 突入を知っているため、**この係数1つが配られれば自力で正しく描ける**。

| | |
|---|---|
| サーバー側の実体 | `internal/game/params.go` の `PatienceParams.LateMul`（既定 **0.6**） |
| 適用箇所 | `internal/game/session.go` の `stepPatience`：`effectiveDt = dtMs / LateMul` |
| 適用範囲 | **全店・全客に一律。来店済みの客にも遡って適用される** |
| 配られないと | **Late 以降、我慢ゲージが約1.67倍ズレ続ける。** 我慢ゲージは主要UIのため実害が大きい |

**残る未回答**：上記 `LateMul` に加えて、客のムード3段階（`irritatedThreshold` / `angryThreshold`）と離脱アラート（`patienceAlertMs`）。**後者2つは表示のみで実害が小さい**ため、当面はクライアント固定値で進める。

> **`patienceAlertMs` はサーバー側に実体がある。** `internal/game/params.go` の `PatienceParams.AlertMs`（既定 **2000ms**）。ただし**サーバー実装では一切使われておらず**（定義と既定値のみ）、実質クライアント向けの表示閾値として置かれている。配信されていないため、公開を依頼する価値がある（[SV-03](./01-プロトコル契約の差分.md#sv-03) の `LateMul` と併せて1件の依頼にまとめられる）。

### 論点

以下の閾値が決まらないため、複数の `.sdd` 仕様書が未確定のまま止まっている。いずれも**表示の区分**にしか使わないが、ゲーム側の実パラメータとズレると表示が嘘になる。

| 用途 | 必要な値 | ズレたときに起きること |
|---|---|---|
| 店の評価3段階（緑/黄/赤） | ~~`highThreshold` / `midThreshold`~~ → **`stormThresholdPct` は v0.3.0 で配信済み** | ~~「赤＝淘汰圏」の意味を持たせる場合、サーバーの `stormThresholdPct` とズレると誤警告になる~~（解決） |
| 客のムード3段階 | `irritatedThreshold` / `angryThreshold` | 表示だけの問題で実害は小さい |
| 離脱アラート表示 | `patienceAlertMs`（用語集7章） | 警告が早すぎ/遅すぎる |

### 決めたいこと

1. 残る閾値（ムード3段階・離脱アラート）をクライアント固定値にしてよいか（サーバー調整に追従しなくてよいか）
2. ~~追従が必要なものだけ `GameParametersPublicSubset` に追加できないか。**特に `stormThresholdPct`**~~ → **v0.3.0 で追加され解決**
3. 各閾値の推奨値（サーバー側のバランス調整の実感として、どのあたりが「危険」か）

### クライアント側の現状の想定

- 評価3段階は**相対順位の表示**として確定済み（[03-決定ログ.md](./03-決定ログ.md) の D-01）。`evalNormalized` が生存店内パーセンタイルであるため、閾値を固定すると常に一定割合が各帯に入る
- 各仕様書の「未確定事項」に閾値を残したまま、骨格のみ先に確定させている

### 決定

**部分的に確定（2026-08-06 / Proto v0.3.0）。** `stormThresholdPct` / `finalStageAliveThreshold` / `finalRushAliveThreshold` はサーバー配信となり、クライアント固定値にしない。

**未回答：`Patience.LateMul`（[SV-03](./01-プロトコル契約の差分.md#sv-03) から移管・最優先）**、ムード3段階、離脱アラート。本項目は閉じない。依頼は [REQ-02](./04-上流への依頼.md#req-02)。

## SV-21

**状態**: 🟢 確定（2026-08-06 / Proto v0.3.0）
**題目**: 画面上の評価数値（「3.4」）のスケール定義

### 論点

試合画面の案には評価が「3.4」および★の並びで表示されているが、これが何の値なのかが決まっていない。候補は以下。

| 候補 | 問題 |
|---|---|
| `evalRaw` をそのまま表示 | 内部スコアであり、取り得る範囲が不明。EMA の生値なので直感的な意味を持たない |
| `evalNormalized`(0..1) を5倍して星換算 | パーセンタイルなので、自分が何もしなくても他店の変動で数字が動く |
| **表示専用の別スケールをサーバーが配信** | ~~契約追加が必要~~ → **v0.3.0 で追加された** |

### 決定

**3案（表示専用スケールをサーバーが配信）で確定。** `EvaluationUpdate.starRating` として届く。

1. **「3.4」が何の値か** → `starRating`。定義は `starRating = 5 * (maxStores - rank) / (maxStores - 1)`
2. **母集団** → **生存店ではなく99店全体**（脱落店は下位に積む）。したがって、他店が脱落しても自店の星は下がらない。これが `evalNormalized`（生存店内パーセンタイル）を直接使わなかった理由
3. **星の段階数** → 連続値（`double`）で届く。0.5刻み等の丸めは表示側の裁量
4. **クライアントで算出しない。** Proto PR #4 いわく「クライアントに算出させると**プレイヤーごとに違う星が見える**」

> **`starRating` と `evalNormalized` は別物。** 分配重み・下位淘汰はサーバーが `evalNormalized` を使い続ける。`starRating` は**表示専用**であり、ゲームロジック上の意味を持たせない。

### 影響

評価の増減表示（[SV-06](./01-プロトコル契約の差分.md#sv-06)）の「量」の単位も `starDelta`（星の増減量）として同時に確定した。画面案の「★+0.2」がそのまま `starDelta` に対応する。

- [ ] `pureC#/docs/.sdd/value-objects/02-store-state.md`（`StoreState` に `StarRating` / `StarDelta` を追加）

## SV-22

**状態**: 🟢 確定（2026-08-06 / [D-09](./03-決定ログ.md#d-09--client-integrationmd-の読み合わせによる確定)）
**題目**: `initialLife` が可変のときの提灯レイアウト

### 決定

**`initialLife` は 3 とする。** サーバー担当と協議のうえ確定した。

> 結合仕様書 §3.2 の例には `"initialLife": 20` とあるが、**これは例値であり 3 で進める**。サーバー側のドキュメントは変更しない。

これにより [D-04](./03-決定ログ.md#d-04--信用ライフの表示は提灯の点灯数で表す)（提灯3つ）と [D-06](./03-決定ログ.md#d-06--99店ミニ盤面のタイル画像は信用ライフを表す評価ではない)（`Life3`/`Life2`/`Life1`）は**改訂不要**。20 を前提にした残存率ベースへの作り替えは行わない。

**ただし防御は残す。** `initialLife` は運営UIから変更可能なパラメータであることに変わりはないため、既存仕様書の「4以上は `Life3` にクランプ」「`Lanterns` の長さ = `initialLife`」はそのまま維持する。

なお `CreditUpdate.delta` は属性ごとに異なり、**`Buzz` の離脱は -2**（他は -1）。ライフ3では**Buzz1人の離脱で残り1**になるため、提灯が一度に2つ消える演出を想定しておく。

### 事実

`initialLife` は `GameParametersPublicSubset` に含まれる＝**試合ごとに変わり得る**。用語集6章の例は3。

### 論点

信用ライフは画面左上の提灯で表現する（[03-決定ログ.md](./03-決定ログ.md) の D-04 と同時に整理）。現在の画面案は提灯3つ前提のレイアウトになっている。

### 決めたいこと

1. `initialLife` が実際に試合ごとに変わる運用をするのか、事実上固定（3）なのか
2. 変わり得る場合、想定される最大値（レイアウトが破綻しない上限を知りたい）

### クライアント側の現状の想定

[Unity/docs/.sdd/value-objects/04-credit-life-lantern-state.md](../../Unity/docs/.sdd/value-objects/04-credit-life-lantern-state.md) では提灯の数を `initialLife` に連動させる設計にしてあり、レイアウトの上限のみ未確定として残している。
