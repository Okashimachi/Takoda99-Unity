## D-11 — 我慢ゲージはクライアント側で計測する

- **日付**: 2026-08-06
- **決定者**: クライアント側（サーバー調整不要。ただし `LateMul` の公開は別途依頼）
- **関連項目**: [SV-03](./01-プロトコル契約の差分.md#sv-03)（🟢 これで閉じる）/ [SV-20](./02-パラメータと閾値.md#sv-20)（`LateMul` を移管）

### 決定

**我慢ゲージの残量はクライアント側で計測する。サーバーへ同期メッセージを要求しない。**

1. **起点は `CustomerView.patienceStartedAtServerMs`**（試合開始からの経過ms）。`patienceMaxMs` からカウントダウンする
2. **時刻同期は不要。** 起点は `MatchState.ElapsedMs` と同じ土俵の値で、`MatchStart` 受信を 0 とした自前の時計とそのまま突き合わせられる
3. **離脱の確定は常に `CustomerLeft` の受信。** 表示が 0 になっても行列から除去しない。0 で止めてサーバー確定を待つ（[02-customer-mood-state.md](../../Unity/docs/.sdd/value-objects/02-customer-mood-state.md) の `TurnedAway` はこの待ち時間の演出状態）
4. **Late の加速もクライアントが計算する。** `PhaseChange` で Late 突入を知っているため、係数さえあれば自力で描ける

### 背景

[SV-03](./01-プロトコル契約の差分.md#sv-03) は当初「残量を運ぶメッセージが無い」ことを問題として立てたが、v0.3.0 で起点（`patienceStartedAtServerMs`）が配られたことで、**残量そのものを同期する必要が無くなった**。

サーバーが残量を毎tick配信する案は、99店×行列分のペイロードが増えるうえ、**我慢ゲージは 150ms 刻みの離散値ではなく滑らかに描きたい**ため、どのみちクライアント側の補間が要る。**最初から全部クライアントで計算する方が単純。**

### 根拠

用語集7章「我慢ゲージの確定はサーバー権威、クライアントは表示専用カウントダウン」と完全に一致する。**表示はクライアント、確定はサーバー**という分担が守られており、[docs/rules/01](../rules/01-責務と絶対原則.md) のサーバー権威の原則にも抵触しない（クライアントが持つのは表示用の推定値だけで、離脱の判定はしない）。

### `LateMul` の扱い

**[SV-03](./01-プロトコル契約の差分.md#sv-03) から [SV-20](./02-パラメータと閾値.md#sv-20) へ移管する。**

`Patience.LateMul` が公開されていない問題は残るが、これは**メッセージ設計の問題ではなくパラメータ公開の問題**。SV-03 は「同期メッセージが無い」という契約の論点なので、クライアント計測で確定した時点で閉じてよい。依頼は [REQ-02](./04-上流への依頼.md#req-02) に同梱済み。

### 影響範囲

- `docs/server-sync/01-プロトコル契約の差分.md`（SV-03 を 🟢 で確定）
- `docs/server-sync/02-パラメータと閾値.md`（SV-20 に `LateMul` を移管・最優先として記載）
- [ ] `Unity/docs/.sdd/03-patience-timer.md`（未作成）— 本決定を前提に書く
- [ ] `pureC#/docs/.sdd/value-objects/03-customer-state.md` — 記載済みだが、`LateMul` 未公開時の暫定挙動を追記する余地あり

### 個別の根拠

#### SV-08 — 試合中の再接続は「決めなかった」のではなく「成立しない」

`internal/app/app.go` がマッチング結果から `conns` を1度だけ組み、`room.New(sess, conns, …)` へ渡して `rm.Run(ctx)` する。**実行中の `Room` に接続を足す API が無い。**

切断時の実挙動も確認した：

- `Room.readConn` は受信チャネルが閉じたら `return` するだけ
- `dispatch` の送信は `_ = c.Send(env)` で**エラーを捨てている**
- したがって**切断＝即脱落ではない。** セッションは切断を知らず、客を割り当て続け、我慢ゲージも減り続ける
- 誰も打たないので客が離脱し続け、**最終的に `SelfCollapse` で緩やかに自滅する**

クライアントは切断時に専用画面を出し、**自動リトライしない**（戻れる先が無いため無意味）。用語集1章の「1試合1接続」と実装は完全に整合している。

> **残る懸念として記録：** WebGL でタブが非アクティブになり WebSocket が切れるのは通常プレイ中に十分起こり得る。プレイヤーに非が無いのに試合を失う。これは**サーバー設計の課題**であり、プロダクトとして必要になった時点で「実行中 Room への再入室」＋「完全状態の再同期メッセージ」の新設として起票する。**クライアント単独では着手できない。**

#### SV-14 — `orderCount` は属性固定・最大 4

`internal/game/params.go` の `AttributeSpec`：`Normal` 2 / `Bonus` 2 / `Claimer` 1 / `Buzz` 4。生成時に `orderCount: spec.OrderCount` を入れるだけで、他に書き換える箇所は無い。

**火力（`heatLevel`）は `orderCount` に影響しない。** `stepHeat` が決めた段階の用途は `WordSource` の**語彙選択**であり、単語の**数**ではなく**難しさ**が変わる。

用語集4章の「4/6/8/12等」は現行実装と一致しない。

> **⚠ 別の設計論点が出た。** `TypedWordCount ≤ 4` なので、24穴の台で焼ける穴は最大4つ。[D-05](#d-05--たこ焼き台の生地マス数は評価で決まる注文個数ではない) は「評価が上がると台が賑やかになる」ことを狙って生地マス数を 12/18/24 にしたが、**評価が高いほど焼けていない生地が目立つ**という逆の見え方になり得る。契約の問題ではなく演出設計の問題なので SV-14 は閉じ、**D-05 の見直しとして実機確認後に別途扱う**。

#### SV-16 — ミラーを手で直さない理由

「Go 正典に既にあるのだから写し間違いの訂正では」という解釈は成り立ち得るが、採らない。

1. **ミラーの価値はバイト一致にある。** v0.3.0 追従時、`diff vendor/Messages.cs upstream` の一致で正しさを担保した。一度手で書き換えると、以後「こちらの修正」と「上流のドリフト」を区別できなくなる
2. **上流が別の形で直す可能性がある。** `omitempty` に対応するのが既定値省略か `WhenWritingNull` かを我々が決め打ちすると黙って食い違い、**型エラーにならず実行時に表示名が消えるだけ**なので気付けない
3. **急いでいない。** マッチング画面自体が未実装

発動条件付きの逃げ道（上流の対応が遅れて実装がブロックされる場合のみ・人間承認要）は [SV-16](./01-プロトコル契約の差分.md#sv-16) に記載。**封筒を手組みして注入する案は採らない**（原則7に正面から抵触）。

## D-09 — `client-integration.md` の読み合わせによる確定

- **日付**: 2026-08-06
- **決定者**: サーバー担当との協議＋クライアント側判断
- **一次資料**: [Takoda99-Server `docs/client-integration.md`](https://github.com/Okashimachi/Takoda99-Server/blob/main/docs/client-integration.md)（裏取り `4ee201c` / proto v0.3.0）

### 決定

### 個別の決定

#### 1. 表示名は実装する（SV-11）

自店名の送信と他店98店の名前取得を実装する。**まだ試合画面しか無いため、試合前のマッチング画面ごと新規に作る。**

**`MatchmakingJoin.displayName` は Go 正典が正しく、C# ミラーが追従漏れしている。** Proto のコミット `d567a98` が Go のみを変更し v0.3.0 で拾われなかったもの。**このリポジトリでミラーを直さず、上流へ修正を依頼する**（絶対原則7）。

**依頼スコープは C# のみ**とする。TS ミラーも同じ追従漏れがあるが、takoda99-unity は C# しか使わないため、要否の判断は Proto 側に委ねる。

反映先：[Unity/docs/.sdd/matchmaking/](../../Unity/docs/.sdd/matchmaking/README.md)（新規作成）

#### 2. `initialLife` は 3（SV-22）

結合仕様書 §3.2 の例が `20` だったが、サーバー担当と協議のうえ **3 で進める**。**サーバー側のドキュメントは触らない。**

これにより [D-04](#d-04--信用ライフの表示は提灯の点灯数で表す)（提灯3つ）と [D-06](#d-06--99店ミニ盤面のタイル画像は信用ライフを表す評価ではない)（`Life3`/`Life2`/`Life1`）は**改訂不要**。当初 20 を前提に検討した残存率ベースへの作り替えは行わない。

> ただし `initialLife` は運営UIから変更可能なパラメータであることに変わりはない。既存仕様書の「4以上は `Life3` にクランプ」「`Lanterns` の長さ = `initialLife`」という防御は**そのまま残す**。

#### 3. 客は行列の先頭のみ対応する（SV-04）

**客を選ぶという行為は一切発生しない。** 打鍵の対象は常に行列の先頭1人。

サーバーは先頭以外への `OrderServed` を**黙って破棄する**（応答も返らない）。したがって：

- 入力対象を選択するUI・操作を設けない
- `CustomerArrived` の到着順を厳密に保持し、先頭から捌く
- 提供したのに `EvaluationUpdate` が返らなければリジェクトと判断する（[結合仕様書 §5.2](https://github.com/Okashimachi/Takoda99-Server/blob/main/docs/client-integration.md)）

#### 4. 我慢ゲージの加速は Late のみ・評価とは無関係（SV-03）

「評価の高い店ほどゲージが速くなるのでフェーズ短縮は不要では」という仮説を検証するため、サーバー実装 `internal/game/session.go` の `stepPatience` を読んだ。

**仮説は成り立たなかった。** 詳細は [SV-03](./01-プロトコル契約の差分.md#sv-03) の「サーバー実装の調査結果」。要点：

- 速度が変わるのは **`phase == Late` のときだけ**。評価は一切参照されない
- 倍率は `1 / LateMul`（既定 0.6 → 約1.67倍速）で、**全店・全客に一律**
- **来店済みの客にも遡って適用**され、`patienceMaxMs` は書き換わらない
- 評価が上がって起きるのは**客の分配が増える**ことであり、1人あたりの減る速度は変わらない（＝「忙しさ」は行列の長さで表現されている）

**したがって Late の加速は独立した仕様として残り、クライアントは `LateMul` を知らないと Late 以降のゲージを正しく描けない。** `Patience.LateMul` の公開を依頼する必要がある。

### 背景

このディレクトリの記載はすべて v0.2.0 時点の Proto を前提に書かれており、**まだ1件もサーバー担当へ共有できていない**状態だった。にもかかわらず、上流側で issue #3 として同種の論点が整理され、v0.3.0 で対応された。結果として `SV-06` / `SV-15` / `SV-21` は**こちらから提起する前に解決した**。

### 根拠（なぜサーバーが配るのか）

追加された4種のフィールドは、いずれも**クライアントに推測させないため**という一貫した理由を持つ（Proto PR #4）。これは [docs/rules/01-責務と絶対原則.md](../rules/01-責務と絶対原則.md) のサーバー権威の原則と完全に一致する。

- `starRating` — クライアントに算出させると**プレイヤーごとに違う星が見える**
- `selfAtRisk` — `rank` と閾値の比較という**勝敗に関わる推測をクライアントにさせない**
- `finalRank` — 受信順からの再構成（[SV-15](./01-プロトコル契約の差分.md#sv-15) の3案）を不要にする
- `patienceStartedAtServerMs` — 受信時刻起点だと**遅延ぶんのズレが体験に直結する**

### D-03 との関係

[D-03](#d-03--評価の増減表示はサーバーイベント方式としクライアントで差分計算しない) は**撤回しない**。「クライアントで差分計算しない」という結論はそのまま有効で、実現手段が「新規イベントの追加」から「`EvaluationUpdate` へのフィールド追加」に変わった。

## D-03 — 評価の増減表示はサーバーイベント方式とし、クライアントで差分計算しない

- **日付**: 2026-08-04
- **決定者**: クライアント側の方針決定（**サーバー側の対応が必要**）
- **関連項目**: [SV-06](./01-プロトコル契約の差分.md#sv-06)

### 決定

1. 増減表示のトリガーは「評価が変わったタイミング」ではなく、**一定のタイミング**とする
2. 表示するのは増減量ではなく、**上がったか下がったかの方向**
3. この判定は**サーバーがイベントとして発行**する。クライアントは受け取って表示するだけ
4. **クライアント側で `EvaluationUpdate` の差分を取る実装は行わない**
5. 該当イベントが Proto に未定義のため、型の確定までクライアント側は**保留**

### 背景

当初は「表示している評価値の差分をクライアントで取る」案を検討していた。

### 根拠

評価は EMA・JKバズ加点・クレーマー減点・他店変動によるパーセンタイル再計算が合流した値であり、**クライアントには増減の因果を自分の提供へ帰属させる手段がない**。サーバーがイベントで方向を通知する方式にすることで、クライアントは一切の評価計算を持たずに済み、サーバー権威の原則（[docs/rules/01](../rules/01-責務と絶対原則.md)）とも完全に整合する。

### 影響範囲

- `Unity/docs/.sdd/value-objects/05-rank-bar-and-eval-delta-view-state.md` §4（保留として記載済み）
- Proto へのイベント追加依頼が必要

## D-01 — 店の評価3段階（緑/黄/赤）は相対順位の表示とする

### 決定

店の状態を表す緑/黄/赤の3段階は、**絶対的な巧拙ではなく「今この試合での相対順位」**を表す。「赤＝下手」ではなく「赤＝現在下位グループにいる」を意味する。

### 背景

`evalNormalized` は用語集5章の定義通り「生存店内でのパーセンタイル(0..1)」であるため、固定閾値を引くと**全店の実力に関わらず常に一定割合が各帯に振り分けられる**。この性質を問題として扱うか、意図した仕様とするかの判断が必要だった。

### 根拠

下位淘汰（`ForcedElimination`）が正規化評価の下位を刈る仕様（用語集9章）であるため、相対順位の表示にしておくと**表示の意味と淘汰の危険度が一致する**。

### 影響範囲

- `Unity/docs/.sdd/value-objects/01-store-visual-state.md`（作成済み）
- 閾値の具体値は未確定（[SV-20](./02-パラメータと閾値.md#sv-20)）。赤帯の下限を `stormThresholdPct` と揃える案を候補として記載済み
