# 07 脱落後（観戦中）の淘汰予告の配信

**状態**: 🔴 未確定（サーバー担当と協議予定）
**題目**: 自店が脱落すると `ForcedEliminationWarning` が届かず、秒読みパネルが最後の値で凍る
**関連**: [SV-10](./01-プロトコル契約の差分.md#sv-10)（宛先表の確定）／[SV-05](./01-プロトコル契約の差分.md#sv-05)（`untilMs` の解釈）／[ranking-view/02](../../Unity/docs/.sdd/ranking-view/02-cull-countdown-panel.md)

> **この文書は論点の提示だけで、決定を含まない。** クライアント側の回避実装も入れていない（理由は §5）。
> 合意できたら [03-決定ログ.md](./03-決定ログ.md) へ転記し、`.sdd` 仕様書へ反映する。

## 1. 事実（現在の契約）

[SV-10](./01-プロトコル契約の差分.md#sv-10)（2026-08-06 確定・[結合仕様書 §3 の宛先表](https://github.com/Okashimachi/Takoda99-Server/blob/main/docs/client-integration.md)が正典）のとおり：

> **`ForcedEliminationWarning` は生存店への「個別」配信。** `selfAtRisk` が店ごとに違うため、全体配信ではない

したがって**自店が脱落した瞬間から、この予告は1通も届かない。**

観戦中（`ClientPhase.Spectating`）に届き続けるものと比べると、こうなっている
（クライアントの受入フェーズ表：[`Dispatcher.AcceptedPhases`](../../pureC%23/src/Takoda99.Client/Net/Dispatcher.cs)）。

| メッセージ | `InMatch` | `Spectating` | `Result` |
|---|---|---|---|
| `RankingSnapshot` | ✅ | ✅ | ✅ |
| `RankingDelta` | ✅ | ✅ | — |
| `StoreEliminatedBatch` | ✅ | ✅ | ✅ |
| `EvaluationUpdate` / `DifficultyUpdate` | ✅ | ✅ | — |
| **`ForcedEliminationWarning`** | ✅ | **❌ 届かない** | — |

クライアント側の受入フェーズには `Spectating` が入っている（＝**受け取る用意はある**）。
届かないのはサーバーの宛先の問題であり、クライアントが弾いているわけではない。

## 2. 何が起きるか

`RankingCanvas/CullPanel`（[ranking-view/02](../../Unity/docs/.sdd/ranking-view/02-cull-countdown-panel.md)）は
「次の足切りまでの秒読み」と「脱落予定の店」を出す常設パネル。予告が来なくなると、最後に受けた1通が残り続ける。

| 表示 | 脱落後の挙動 |
|---|---|
| 残り秒 | `RemainingMsAt` が 0 を返し続け、**「あと0秒」を出したまま止まる** |
| 脱落予定の店（最大5行） | **1つ前の段階の顔ぶれのまま**残る |
| 段階（`3 / 6`） | 最後に受けた値のまま止まる |
| 境界順位（`12位以下が脱落`） | 同上 |

**ランキング（左右のパネル・オーディエンスパネル）は更新され続ける**ため、
「順位は動いているのに、秒読みだけ 0 で止まり、脱落予定の顔ぶれが実際の順位と合っていない」という
矛盾がそのまま画面に出る。

## 3. なぜ重要か

99人中98人は「脱落してから試合終了まで」を**観戦者として過ごす**。

- **次に誰が切られるかは観戦の見どころ**そのもの（[ranking-view/07 §2](../../Unity/docs/.sdd/ranking-view/07-audience-panel.md)）
- 淘汰は残り10人・120秒の最終ステージまで続く。**脱落が早いほど、凍った画面を見る時間が長い**
- 秒読みは予選の我慢ゲージに代わる「時間の緊張」の担い手であり、リザルトまでの間の主要な情報源

## 4. クライアントだけでは解決できない

**順位と `cutLineRank` を比較して「次に落ちるのは誰か」を割り出すことは禁止**している
（[docs/rules/01](../rules/01-責務と絶対原則.md)：クライアントに下位淘汰の判定を持たせない。サーバー権威）。

残り時間についても、次の足切りの締切は `untilMs` にしか入っておらず、
観戦者が受け取れるどのメッセージからも導けない（`StoreEliminatedBatch` は**実行された後**に届く）。

> **したがって、これはクライアント実装の問題ではなく配信の問題。**

## 5. クライアント側の回避実装を入れていない理由

「残り秒を `--` にして脱落予定リストを畳む」ところまではクライアント単独でできるが、**入れていない。**

- 情報が更新されるようになるわけではなく、**表示の劣化を固定するだけ**
- 配信が直れば**すぐ不要になる**コードと仕様（VOのフラグ・分岐・テスト）が残る
- どう見せるかは「脱落後も秒読みを出すのか」という**企画判断とセット**であり、
  §6 の選択肢3（送らないと決める）を選んだ場合に初めて必要になる

**現状は「最後に受けた値で凍る」ままにしてある。** 協議の結果を待ってから作る。

## 6. 選択肢（サーバー側の判断が要る）

`selfAtRisk` が宛先ごとに違うため、そのままの全体配信にはできない。

| # | 案 | 変更の規模 | 備考 |
|---|---|---|---|
| **1** | 脱落済みの店にも `ForcedEliminationWarning` を送る（`selfAtRisk` は常に `false`） | **宛先表の変更のみ** | 契約（メッセージ・型）を変えずに済む。クライアントは**修正不要**（受入フェーズに `Spectating` が入っており、そのまま描ける） |
| 2 | `selfAtRisk` を持たない**観戦者向けの全体配信**メッセージを新設（`untilMs` / `stageIndex` / `stageTotal` / `cutLineRank` / `cutStoreIds`） | Proto の変更が必要 | 生存店への個別配信と分離できる。ただし [Proto へ依頼](./04-上流への依頼.md)が必要で、往復が増える |
| 3 | 送らない（＝**脱落後は秒読みを出さない**と決める） | 変更なし | クライアント側でパネルを畳む実装が必要。観戦中の情報は「ランキング」だけになる |

**クライアントとしては 1 を希望する。** 契約を変えずに済み、こちら側の修正も要らない。

### 1 を採る場合に確認したいこと

- 脱落済みの店へ送る `selfAtRisk` は `false` 固定でよいか（`true` が来ることはないと決めてよいか）
- `cutStoreIds` は生存店へ送るものと**同一内容**でよいか（宛先で中身を変えないか）
- 配信頻度は生存店と同じ 1〜2Hz でよいか。**98人ぶん増える送信量**が問題にならないか
  （[SV-17](./01-プロトコル契約の差分.md#sv-17) でマッチング中の全員配信を避けた経緯があるため、ここも量を確認したい）
