## SV-01

**状態**: ⚪ 対応不要（2026-08-06 / [D-09](./03-決定ログ.md#d-09--client-integrationmd-の読み合わせによる確定)）
**題目**: `EvaluationUpdate` に `storeId` が無く自店専用

> **他店の評価は不要と判断したため、本項目は閉じる。** 98店ミニ盤面の見た目は評価ではなく**信用ライフ**で決まる（[D-06](./03-決定ログ.md#d-06--99店ミニ盤面のタイル画像は信用ライフを表す評価ではない)）。`StoreSummary` には `evalNormalized` / `rank` も入っており 250ms ごとに届くため、将来必要になっても `StoreListUpdate` から取れる。
>
> ただし**下記「クライアント側への影響」の仕様書の誤りは実在する**ため、修正は行う。

### 事実（Proto）

```csharp
public sealed class EvaluationUpdate
{
    public double EvalRaw { get; set; }
    public double Normalized { get; set; } // 0..1
    public int Rank { get; set; }
    public int AliveCount { get; set; }
    public double StarRating { get; set; } // v0.3.0 追加・表示専用 0..5
    public double StarDelta { get; set; }  // v0.3.0 追加
}
```

v0.3.0 で `starRating` / `starDelta` が増えたが、`storeId` は依然として無い。`storeId` を持たないため、このメッセージは**自店の評価のみ**を運ぶと解釈される。`CreditUpdate` も同様に `storeId` を持たない（`life` / `delta` / `reason` のみ）。

### 論点

他店（99店ミニ盤面）の評価・信用は `StoreListUpdate`（`List<StoreSummary>` のフルスナップ）でしか取得できないことになる。この理解で正しいか。

### クライアント側への影響

**本リポジトリの仕様書に誤りがある。** [02-store-state.md](../../pureC%23/docs/.sdd/value-objects/02-store-state.md) は「`EvaluationUpdate` の対象 `StoreId` が自店なら `StoreState`、他店なら `StoreSummaryState` を更新」と書いているが、Proto 上そのような分岐は成立しない。正しくは:

- `EvaluationUpdate` / `CreditUpdate` → 自店の `StoreState` のみ更新
- `StoreListUpdate` → 全店の `StoreSummaryState` を一括置換

### 決めたいこと

1. 上記の理解で正しいか
2. 正しい場合、他店の評価更新の粒度は `StoreListUpdate` の頻度に完全に依存する（→ [SV-02](#sv-02)）

**題目**: `StoreListUpdate` の配信頻度（「低頻度」の実値）

### 決定

1. **配信間隔は 250ms ごと**、全員へ全店分。**tick（150ms）とは別系統**で回っている
2. 試合中の頻度変更は無い

`StoreListUpdate` に「99店概況の低頻度フルスナップ（差分版は将来の帯域対策）」とコメントがあるのみで、頻度は契約に含まれない。

### 論点

99店ミニ盤面の更新頻度がそのままプレイ体験（他店の状況がどれだけリアルタイムに見えるか）を決める。

2. 試合中に頻度を変えるか（終盤だけ上げる等）
3. 生存数 `aliveCount` は `EvaluationUpdate` にも含まれるが、両者で値がズレた場合はどちらを優先するか

## SV-03

**状態**: 🟢 確定（2026-08-06 / [D-11](./03-決定ログ.md#d-11--我慢ゲージはクライアント側で計測する)）
**題目**: 我慢ゲージ残量を同期するメッセージが存在しない

### 事実（Proto v0.3.0）

- `CustomerView`（`CustomerArrived` のペイロード）は `patienceMaxMs` と **`patienceStartedAtServerMs`（v0.3.0 追加・サーバー基準の単調時刻 ms）** を持つ
- **`patienceLeftMs`（残量）を運ぶメッセージは依然として存在しない**
- 客が離脱したことは `CustomerLeft`（`customerId` / `reason: Timeout`）で事後的に届く

つまり現契約では、クライアントは `patienceStartedAtServerMs` を起点に `patienceMaxMs` を**ローカルでカウントダウンし、`CustomerLeft` が来たら離脱として扱う**。

**v0.3.0 で解決した点**：ゲージの起点が「クライアントの受信時刻」から「サーバー基準の時刻」になったため、**受信遅延ぶんのズレが表示に出なくなった**（Proto PR #4：ゲージが主要UIに昇格したことが追加理由）。ただしサーバー時刻とクライアント時計の対応づけ（オフセット推定）は契約に無く、クライアント側の実装事項として残る。

### 論点

用語集7章は「我慢ゲージの確定はサーバー権威、クライアントは表示専用カウントダウン」としており、契約はこの方針と整合している。一方で、以下が保証されないと表示とサーバー実態がズレる。

- **★`Late` フェーズで減る速度が 1/`LateMul` 倍になる。クライアントは倍率を知る手段が無い**（下記「サーバー実装の調査結果」）
- タブ非アクティブ（WebGL）でクライアントのカウントが遅れる（`patienceStartedAtServerMs` 起点なら復帰時に正しい値へ復元できるため、v0.3.0 で影響は小さくなった）
- ~~`patienceStartedAtServerMs` とクライアント時計の対応づけ~~ → **論点として存在しない。** これは絶対時刻ではなく**試合開始からの経過ms**（`MatchState.ElapsedMs` と同じ土俵）であり、時刻同期は不要

### サーバー実装の調査結果（2026-08-06）

`Takoda99-Server` の `internal/game/session.go` `stepPatience` を確認した。

```go
effectiveDt := dtMs
if s.phase == proto.PhaseLate && s.params.Patience.LateMul > 0 {
    effectiveDt = int(float64(dtMs) / s.params.Patience.LateMul)
}
...
c.patienceLeftMs -= effectiveDt   // 行列内の全客に適用
```

| 項目 | 事実 |
|---|---|
| 速くなる条件 | **`phase == Late` のときだけ。** これ以外に速度を変える分岐は無い |
| 倍率 | `1 / LateMul`（既定 `LateMul = 0.6` → 約 **1.67倍速**） |
| 評価との関係 | **無関係。** `stepPatience` は評価を一切参照しない |
| 適用範囲 | **全店・全客に一律。** 対応中(先頭)だけでなく待機中の客も減る |
| 来店済みの客 | **遡って適用される。** Mid に来店した客が待っている最中に Late へ移行すると、その瞬間から加速する |
| `patienceMaxMs` | **書き換わらない。** 来店時の属性ベース値（Normal 16000 / Bonus 18000 / Claimer 12000 / Buzz 24000）のまま。**減る速度だけが変わる** |

> **「評価の高い店ほどゲージが速くなる」という仕組みは実装されていない。** 評価が上がると起きるのは**客の分配が増える**ことで、行列が伸びた結果**同時に減る客が増える**（＝忙しくなる）。1人あたりの減る速度は変わらない。したがって **Late の加速は評価では代替されず、独立した仕様として残る。**

**クライアント側の受け止め（2026-08-06 確定）：ゲージの加速要因はフェーズ進行（＝経過時間）のみでよい。** 評価・店の状態による可変要素は無いものとして設計する。`stepPhase` の移行条件は `aliveCount <= threshold || elapsedMs >= timeMs` なので、実際の引き金は生存数か経過時間のどちらかだが、**クライアントは `PhaseChange` の受信だけを見ればよく、引き金を区別する必要は無い。**

**`LateMul` は `GameParametersPublicSubset` に含まれない。** クライアントは `PhaseChange` で Late 突入を知れるので、**倍率さえ配られれば自力で正しく計算できる**。この1点は [SV-20](./02-パラメータと閾値.md#sv-20) へ移管した（依頼は [REQ-02](./04-上流への依頼.md#req-02) に同梱）。

### 決めたいこと（すべて決着済み）

1. ~~我慢ゲージのローカルカウントダウンで運用する前提でよいか~~ → **そうする**（下記「決定」）
2. ~~`Patience.LateMul` を公開できないか~~ → **[SV-20](./02-パラメータと閾値.md#sv-20) へ移管**（メッセージ設計ではなくパラメータ公開の問題のため）
3. ~~`Patience.AlertMs` を公開できないか~~ → **[SV-20](./02-パラメータと閾値.md#sv-20) へ移管**（同上）
4. ~~表示が0でも `CustomerLeft` が来ない場合の扱い~~ → **0 で止めて待つ**（下記「決定」3）

### クライアント側の現状の想定

[02-customer-mood-state.md](../../Unity/docs/.sdd/value-objects/02-customer-mood-state.md) では、表示が0に達した時点で `TurnedAway`（退転演出）に入り、**行列からの実除去は `CustomerLeft` 受信まで待つ**設計にしてある。**この方針で確定。**

### 決定

**確定（2026-08-06）。我慢ゲージはクライアント側で計測する。**

1. **残量の同期メッセージは要求しない。** サーバーは残量を配信せず、クライアントが `patienceStartedAtServerMs`（試合開始からの経過ms）を起点に `patienceMaxMs` からカウントダウンする
2. **時刻同期も不要。** 起点は `MatchState.ElapsedMs` と同じ土俵の値であり、`MatchStart` 受信を 0 とした自前の時計とそのまま突き合わせられる
3. **離脱の確定は常に `CustomerLeft` の受信。** クライアントの表示が 0 になっても、それだけで行列から除去しない（表示が先行し、実除去はサーバー確定を待つ）
4. **Late の加速もクライアントが計算する。** `PhaseChange` で Late 突入を知っているため、係数さえあれば自力で正しく描ける

> **本項目（＝「同期メッセージが無い」という契約の論点）はこれで閉じる。**
>
> 残るのは **`Patience.LateMul` という1つの数値が公開パラメータに無い**という点だけであり、これはメッセージ設計ではなく**パラメータ公開の問題**。したがって [SV-20](./02-パラメータと閾値.md#sv-20) へ移管する（依頼は [REQ-02](./04-上流への依頼.md#req-02) に同梱済み）。

## SV-04

**状態**: 🟢 確定（2026-08-06 / [D-09](./03-決定ログ.md#d-09--client-integrationmd-の読み合わせによる確定)）
**題目**: 行列（`StoreQueue`）を配信するメッセージが無い

### 決定

1. **クライアントがローカルに組み立てる**で正しい
2. **`CustomerArrived` の到着順 = 行列の並び順。** サーバー側で並び替えは起きない
3. 他店の行列長は `StoreSummary` に含まれず、**表示しない**

> **★最重要：客は行列の先頭からしか提供できない。** 先頭以外への `OrderServed` は**黙って破棄され、応答も返らない**（[結合仕様書 §2.3 / §5.1](https://github.com/Okashimachi/Takoda99-Server/blob/main/docs/client-integration.md)）。
>
> したがって**客を選ぶという操作は一切発生しない**。打鍵の対象は常に行列の先頭1人に固定する。提供したのに `EvaluationUpdate` が返らなければリジェクトと判断するしかない（§5.2「リジェクトは無応答」）。
>
> また**待機中の客も我慢ゲージが減っている**（先頭だけではない）。これが行列を溜めること自体のコストであり、UIもそう描く。

### 事実（Proto）

行列の内容・長さを運ぶメッセージは存在しない。`CustomerArrived` / `CustomerLeft` の積み重ねからクライアントがローカルに構築するしかない。

### 論点

- 行列長は客分配の重み（`÷(行列長+1)`、用語集3章）に効く重要な値だが、クライアントは自分の行列を推測で持つことになる
- サーバー側の行列とクライアントの行列がズレた場合（メッセージの取りこぼし・再接続）、復旧手段が無い（→ [SV-08](#sv-08)）

### 決めたいこと

1. クライアントがローカルに行列を組み立てる前提でよいか
2. `CustomerArrived` の到着順 = 行列の並び順として扱ってよいか（サーバー側で並び替えが起きないか）
3. 他店の行列長を表示する予定はあるか（現状 `StoreSummary` に含まれない）

## SV-05

**状態**: 🟡 確認待ち（v0.3.0 で**予告UIの実装可能性は回復**。残り時間の表示可否のみ未回答）
**題目**: `ForcedEliminationWarning.untilTick` が解釈できない

### 事実（Proto v0.3.0）

```csharp
public sealed class ForcedEliminationWarning
{
    public int UntilTick { get; set; }
    public double ThresholdPct { get; set; }
    public bool SelfAtRisk { get; set; } // v0.3.0 追加
}
```

`untilTick`（あと何 tick で下位淘汰か）を受け取るが、**クライアントは tick の長さ（`tickIntervalMs`）も現在の tick 番号も受信していない**。`GameParametersPublicSubset`（v0.3.0）にも含まれない（`initialLife` / `maxStores` / `stormThresholdPct` / `finalStageAliveThreshold` / `finalRushAliveThreshold`）。

### サーバー実装の調査結果（2026-08-06）— 下位淘汰(storm)の全体像

`internal/game/session.go` の `stepStorm` / `cullCandidates` / `executeCull` を読んだ。

#### タイミング

```go
s.stormTickCounter++                              // 毎tick 1..IntervalTicks
warnAt := sp.IntervalTicks - sp.WarnTicks         // 140 - 30 = 110
if s.stormTickCounter == warnAt && !s.stormWarnSent {
    remaining := sp.IntervalTicks - s.stormTickCounter   // = WarnTicks
    ... ForcedEliminationWarning を生存店へ個別配信 ...
}
if s.stormTickCounter < sp.IntervalTicks { return }
s.stormTickCounter = 0; s.stormWarnSent = false
out = s.executeCull(out)
```

| 値 | 既定 | 実時間（tick = 150ms） |
|---|---|---|
| `Storm.IntervalTicks` | 140 | **21秒ごとに淘汰が起きる** |
| `Storm.WarnTicks` | 30 | **淘汰の4.5秒前に予告** |
| `Storm.ThresholdPct` | 0.10 | 生存店の**上位90%が残り、下位10%が刈られる** |

#### ★ `untilTick` は常に `WarnTicks` と同じ値になる

予告は `stormTickCounter == warnAt` の**1tickだけ**発火し、そのとき `remaining = IntervalTicks - warnAt = WarnTicks`。つまり **`untilTick` は毎回 30 で固定**であり、カウントダウンしない。`stormWarnSent` フラグにより1周期に1回しか送られない。

**したがって `untilTick` は「予告から実行までのリードタイム」を伝える定数**であって、可変の残り時間ではない。クライアントが刻々と減る値を受け取るわけではない。

#### 刈られる店数

```go
cullCount := int(float64(len(alive))*sp.ThresholdPct + 0.999999)  // 実質 ceil
if cullCount < 1 { cullCount = 1 }
if cullCount >= len(alive) { cullCount = len(alive) - 1 }
```

**毎回必ず1店以上が落ちる**（生存2店以上なら）。これが「制限時間が無くても試合が終わる」保証で、結合仕様書 §4 の「決着は storm が保証する」の実体。生存1店になったら `stepStorm` は何もしない。

#### ★ `selfAtRisk` は予告時点のスナップショットで、確定ではない

予告と実行は**同じ関数 `cullCandidates()` を共有**する（サーバー側コメント：「予告と実行で別々に判定すると、予告が嘘になったり『警告が出ていないのに落ちる』が起きる」）。

**しかし `executeCull` は4.5秒後に `cullCandidates()` を再評価する。** ロジックは同じでも入力状態が変わるため、**対象は入れ替わり得る**。

| 状況 | 起き得るか |
|---|---|
| `selfAtRisk = true` だったが、4.5秒で挽回して助かる | **起きる**（＝予告は行動を促す意味を持つ） |
| `selfAtRisk = false` だったが、4.5秒で順位を落として刈られる | **起きる**（＝`false` は安全の保証ではない） |

**これは仕様のバグではなく、予告に意味を持たせるための設計。** 「あと4.5秒、今から巻き返せば助かる」という緊張感が storm の核心。

> UI設計上の含意：**`selfAtRisk = true` は「終わり」ではなく「今すぐ巻き返せ」の合図**として見せる。逆に `false` を「安全」と見せると、刈られたときに理不尽に映る。

### 論点

**v0.3.0 で `selfAtRisk` が追加され、「自店が淘汰圏内か」はサーバーから直接届くようになった。** これにより「もうすぐ淘汰が来る／自分が対象だ」という**定性的な予告UIは実装できる**（上記の選択肢3に相当する経路が開いた）。

残る論点は、**「あと何秒」という定量表示を出すか**のみ。`untilTick`（＝定数30）を ms へ換算するには `tickIntervalMs` が要るが、公開パラメータに含まれない。

**ただし定量表示をやるとしても、必要なのは最初の1回だけ。** `untilTick` は固定値なので「予告受信 → 4.5秒のカウントダウンをクライアントが自前で回す」形になり、**毎tick の同期は要らない**。`tickIntervalMs` が1つ配られれば `untilTick × tickIntervalMs` で正確なリードタイムが得られる。

なお `selfAtRisk` の追加により、`rank` と `thresholdPct` を突き合わせる推測処理をクライアントに持たせない形になった。これは[サーバー権威の原則](../rules/01-責務と絶対原則.md)と整合するため、**クライアント側で `rank` から淘汰圏を判定する実装は行わない**。

### 決めたいこと

残り時間の定量表示を出す場合、以下のいずれかを選ぶ。

1. `tickIntervalMs` を `GameParametersPublicSubset` に追加する（クライアントが ms 換算する）
2. `ForcedEliminationWarning` のフィールドを `untilMs` に変更する（最も単純）
3. 予告は「もうすぐ来る」という定性的表示に留め、残り時間を出さない（**v0.3.0 の `selfAtRisk` だけで実装できる**）

### 決定

**部分的に確定（2026-08-06 / Proto v0.3.0）。** 淘汰圏内かの判定はサーバーが `selfAtRisk` で配信する。**定量表示の可否（1〜3の選択）は演出方針が決まっていないため本項目は閉じない。**

**当面は選択肢3（定性表示のみ）で実装を進められる。** 定量表示をやると決めた場合にのみ `tickIntervalMs` の公開を依頼する（[README の依頼一覧](./README.md)参照）。判断材料：

| | 定性のみ（選択肢3） | 定量あり（選択肢1） |
|---|---|---|
| 追加の依頼 | **不要** | `tickIntervalMs` の公開が要る |
| 見せ方 | 「淘汰が来る」＋`selfAtRisk` で警告 | 「あと4.5秒」のカウントダウン |
| 緊張感 | 中 | 高（残り時間が見える） |
| 実装 | 予告受信で演出を出すだけ | 受信時刻から自前でカウントダウン |

## SV-08

**状態**: 🟢 確定（2026-08-06 / [D-10](./03-決定ログ.md#d-10--残存-sv-項目の解決sv-08--09--12--14--16)）
**題目**: 再接続・途中復帰時の状態再同期手段が無い

### 事実（Proto）

- `MatchStart` は試合開始時の1回のみを想定した内容（`selfStoreId` / `params` / `phase` / `stores`）
- 試合途中の完全な状態（行列・現在の客・我慢ゲージ残・注文進捗）を取得するメッセージは無い

### サーバー実装の調査結果（2026-08-06）

**試合中の再接続は、契約以前にサーバーの構造として成立しない。**

| 事実 | 根拠 |
|---|---|
| `Room.conns` は**試合開始時に1度だけ**構築され、以後**追加する経路が無い** | `internal/app/app.go` がマッチング結果から `conns` を組み、`room.New(sess, conns, …)` に渡して `rm.Run(ctx)`。実行中の Room に接続を足す API は存在しない |
| 切断は**検知されるが、何も起こらない** | `Room.readConn` は受信チャネルが閉じたら `return` するだけ。`dispatch` の送信は `_ = c.Send(env)` でエラーを捨てている |
| **切断＝即脱落ではない** | セッションは切断を知らないまま進む。客は割り当てられ続け、我慢ゲージも減り続ける |
| 実際には**緩やかに自滅する** | 誰も打たないので客が次々に離脱し、`CustomerLeft` → `CreditUpdate` で信用が削られ、最終的に `SelfCollapse` で脱落する |
| 「再接続」の語は接続上限のコメントにあるだけ | `cmd/server/main.go` の `maxConcurrentConnections`（200）の説明文。実装上の受け皿は無い |

用語集1章の「1試合1接続」「再マッチは接続の張り直し」という記述と、実装は完全に整合している。

### 決定

**クライアントは試合中の再接続を実装しない。**

1. **切断したら、その試合は諦める。** 再接続を試みても Room に戻る手段が無く、成功し得ない
2. **切断時は専用の画面を出す**（「接続が切れました」＋トップへ戻る導線）。**自動リトライを実装しない**（無駄に接続枠を消費するだけ）
3. **切断＝即脱落ではない**ため、`MatchEnd` を受け取れずに終わる。リザルトは表示できない
4. WebGL でタブが非アクティブになり WebSocket が切れた場合も同じ扱い。**復帰させる方法は無い**

> **これは「サーバーに要望を出さない」という決定ではなく、「現状の設計では実装しようがない」という事実の確認。** 将来この体験を改善するなら、サーバー側に「実行中 Room への再入室」と「完全状態の再同期メッセージ」の両方を新設する必要があり、**クライアント単独では着手できない**。プロダクトとして必要になった時点で、改めてサーバー設計の課題として起票する。

### 残る懸念（起票はするが、今回の判断は変えない）

- **WebGL でのタブ非アクティブは、通常のプレイ中に十分起こり得る。** ブラウザがバックグラウンドタブの WebSocket を切ると、プレイヤーは何も悪くないのに試合を失う
- 上記は**サーバー側の設計課題**であり、クライアント側の対策（keep-alive 等）で防げるかは未検証。`01-network-client.md` の作成時に、WebGL の実挙動を確認したうえで再検討する

### 反映先

- [ ] `Unity/docs/.sdd/platform/01-network-client.md`（未作成。切断時の挙動と「再接続しない」方針を明記する）
- [ ] `Unity/docs/.sdd/matchmaking/01-matchmaking-flow.md` §11 の未確定事項を更新

1. **`elapsedMs` / `missCount` はどちらも「注文N個ぶんの合計」。** 単語ごとではなく**客ごとに1回**、`orderCount` 個すべてを打ち切った瞬間に送る
2. **サーバーの丸め**（`ApplyOrderServed`）:
   - `elapsedMs` の下限 = `minMsPerWord × orderCount`。それ未満は下限値に丸められる
   - `missCount` は `[0, サーバーが発行した総打鍵数]` にクランプされる
3. **速く申告しても得しない**（下限で頭打ち）。**ミスを過大申告しても総打鍵数以上にはならない**
4. **リジェクトは無応答。** 破棄条件（試合が進行中でない／自店が脱落済み／`customerId` が存在しない／その客が自店に割り当てられていない／**その客が行列の先頭でない**）に当たると、エラーも応答も返らず黙って捨てられる

> `missCount` の厳密な数え方（1文字ミスごとに +1 か、ローマ字の複数パターン途中入力をミスとするか）は明文化されていないが、**サーバーが総打鍵数でクランプする**ため、クライアントの仮置き（1文字ミスごとに +1）で実害は出ない。分母が総打鍵数である点も用語集4章の精度式と整合する。

### 事実（Proto）

```csharp
public sealed class OrderServed
{
    public string CustomerId { get; set; }
    public int ElapsedMs { get; set; }
    public int MissCount { get; set; }
    public long ClientTimestamp { get; set; }
}
```

`missCount` の**数え方**は契約に書かれていない。

### 論点

用語集4章は「精度 = `1 - (missCount / 総打鍵)`」としているが、`OrderServed` は総打鍵数を送っていない。サーバーは `orderCount` と単語長から総打鍵数を推定していると思われる。

また、以下で値が変わる。

- 1文字ミスするたびに +1 なのか、1単語につき最大1回なのか
- ローマ字入力で複数パターンがある文字（`shi`/`si` 等）の途中入力をミスと数えるか

### 決めたいこと

1. `missCount` の定義（1文字ミスごとに +1 で確定してよいか）
2. サーバーの `SanityCheck`（用語集11章）が弾く下限値（`elapsedMs` の最小値等）。クライアントが正常な範囲を知らないと、正当なプレイが弾かれても気付けない

### クライアント側の現状の想定

[04-order-progress-state.md](../../pureC%23/docs/.sdd/value-objects/04-order-progress-state.md) では「1文字ミスごとに +1」を仮置きし、未確定事項として残している。

### 論点

たこ焼き台を **6列×4行＝24穴** で確定させた（[03-決定ログ.md](./03-決定ログ.md) の D-02）ため、`orderCount` が 24 を超えると台に表示しきれない。

1. `orderCount` の最大値は 24 以下と考えてよいか
2. 火力（`Heat`）上昇で `orderCount` が増える設計か（増えるなら上限の確認が必須）

### クライアント側の現状の想定

**参加者一覧を毎秒フルスナップで配ると、この設計判断と正面から衝突する。** 99人×24文字の名前を毎秒全員へ配ると帯域が跳ね上がる。したがって「`MatchmakingStatus` に `participants[]` を足す」という素朴な案は、そのままでは採れない可能性が高い。**どう配るかはサーバー側の判断に委ねる**必要がある。
