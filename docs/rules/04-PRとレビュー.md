# 04 PRとレビュー

PR（プルリクエスト）を出す・レビューするときのルール。ブランチ/コミットの基本は [03-Git運用.md](./03-Git運用.md)。

---

## 1. PR の流れ

1. `feature/xxx` で作業し、[03-Git運用.md](./03-Git運用.md) のコミット規約に沿ってコミットする。
2. `develop` をベースに PR を作成する（`main` 直接は禁止）。**PR 作成は AI が自由に実行してよい。**
3. PR のタイトルは §2、本文は §3 のテンプレ（[.github/PULL_REQUEST_TEMPLATE.md](../../.github/PULL_REQUEST_TEMPLATE.md) で自動挿入）に沿って埋める。
4. **`develop` / `main` へのマージは人間が行う**（AI は指示があってもマージしない）。

## 2. PR タイトルの規約

コミット規約（[03-Git運用.md](./03-Git運用.md) §3）と揃える。

```
{type}: {概要（日本語・50文字以内）}
```

- `type`: `feat` / `fix` / `refactor` / `docs` / `chore` / `test` / `spec`（コミットと同じ）
- 概要はコミットより少し長くてよい（PR 全体を1行で表す）。末尾に句点は付けない。
- 例:
  - `spec: TypingJudge の .sdd 仕様書を追加`
  - `feat: Dispatcher に未知typeの前方互換処理を実装`
  - `fix: 再接続時に StoreListUpdate を取りこぼす不具合を修正`
  - `refactor: pureC#/src の Store を Client-Docs 04章に合わせて整理`

## 3. PR 説明のテンプレ

実体は [.github/PULL_REQUEST_TEMPLATE.md](../../.github/PULL_REQUEST_TEMPLATE.md)（PR 作成時に自動挿入）。ここに全体像を再掲する。各セクションは埋まらなければ「なし」と書く（空欄で残さない）。

```markdown
## 概要
> この PR で何を・なぜ変えたか（1〜3行）。

## 変更内容
- （箇条書きで差分の要点）

## 関連
- 上流ドキュメント / Issue / 対応する pureC#/docs/.sdd 仕様書:

## テスト
> 確認したこと（どう動かして何を見たか）。proto ver / サーバーモードも記す。pureC#の変更はユニットテスト実行結果も記す。
-

## セルフレビュー（このリポジトリ固有・必須）
- [ ] 経営ロジック（客分配/評価/信用/脱落/下位淘汰/フェーズ/火力/お題単語生成）をC#で計算していない（打鍵判定のみ許可）
- [ ] 打鍵判定は `OrderServed`（注文単位）に集約（1文字送信・勝敗数値のローカル算出なし）
- [ ] 我慢ゲージの離脱をクライアントで確定していない（`PatienceTimer` は表示専用）
- [ ] ローマ字テーブルは Proto の共有データを使用（独自に持たない）
- [ ] proto の型・契約を本リポジトリで書き換えていない
- [ ] 命名がユビキタス言語（用語集）に一致
- [ ] 廃止された旧構想（テキストロ99）の用語・機構を持ち込んでいない（`Daken`/`Combo`/`Attack`/`Ko`/`Zone`等）
- [ ] `pureC#/src` に `UnityEngine` を持ち込んでいない（該当PRの場合）
- [ ] `pureC#/src` の変更は対応する `pureC#/docs/.sdd` 仕様書と整合している（該当PRの場合）
- [ ] 接続先 URL はビルド設定（直書きなし）
- [ ] 秘密情報（本番URL・トークン）を差分に含めていない

## マージ
- [ ] ベースは `develop`（`main` 直接ではない）
- [ ] **`develop` / `main` へのマージは人間が行う**（AI はマージしない）
```

> テンプレを更新するときは、正典である `.github/PULL_REQUEST_TEMPLATE.md` と本節の再掲を両方揃える。

## 4. PR の粒度

- 1 PR は 1 つの関心事に絞る（レビュー可能な大きさに保つ）。仕様書追加と実装は分けてもよいが、対応関係がPR単位・ブランチ単位で追える状態を保つ。
- 判断の経緯・確認したことは PR 本文に書く（別途ドキュメントを作らない）。

## 5. レビュー観点（このリポジトリ固有）

このリポジトリの最重要レビュー観点は **「打鍵判定以外のロジックが混入していないか」**。以下を必ず確認する。

- [ ] 経営ロジック（客分配/評価/信用/脱落/下位淘汰/フェーズ/火力/お題単語生成）をC#で計算していないか（サーバー権威）→ [01](./01-責務と絶対原則.md)
- [ ] 打鍵判定の結果を `OrderServed`（注文単位）に集約しているか（1文字ごと送信・勝敗数値のローカル算出をしていないか）
- [ ] 我慢ゲージの離脱をクライアントで確定していないか（サーバーの `CustomerLeft` 待ちか）
- [ ] ローマ字テーブルを独自に持っていないか（Proto の共有データを使っているか）
- [ ] proto の型・契約をこのリポジトリで書き換えていないか（変更が要るなら Proto 側へ）
- [ ] 命名がユビキタス言語（用語集）に一致しているか → [01](./01-責務と絶対原則.md)
- [ ] 廃止された旧構想の用語・機構を持ち込んでいないか
- [ ] `pureC#/src` に `UnityEngine` 依存が無いか（該当する変更の場合）
- [ ] `pureC#/src` の変更が対応する `.sdd` 仕様書と食い違っていないか（該当する変更の場合）
- [ ] 接続先 URL をビルド設定で切り替えているか（直書きしていないか）
- [ ] 秘密情報（本番URL・トークン）が差分に含まれていないか
